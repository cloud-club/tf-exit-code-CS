## [COMMON-163] SOLID 원칙에 대해 설명해 주세요.

답변:

SOLID 원칙은 객체지향 소프트웨어를 유연하고 유지보수하기 쉽게 설계하기 위한 5가지 설계 원칙입니다. 따라서 단일 책임 원칙(SRP), 개방-폐쇄 원칙(OCP), 리스코프 치환 원칙(LSP), 인터페이스 분리 원칙(ISP), 의존 역전 원칙(DIP)가 존재합니다. 이를 적용하면 유지보수와 테스트가 쉽고 확장성이 증가되며 재사용성이 증가되는 장점이 있습니다.

## [COMMON-164] 단일 책임 원칙이 무엇이고, 왜 중요한지 설명해 주세요.

SRP(Single Responsibility Principle), 즉 단일 책임 원칙은 하나의 클래스는 하나의 책임, 기능만 가져야 하고 클래스가 변경되는 이유는 단 하나여야 한다는 원칙입니다.

그렇기 때문에 유지보수도 쉽고 테스트도 쉽습니다.

## [COMMON-166] 인터페이스를 사용하는 이유와 장단점을 설명해 주세요.

답변:

인터페이스란 클래스가 구현해야 할 기능의 규약을 정의하는 역할을 합니다. 무엇을 할 수 있는지만 정의하고 어떻게 하는지는 구현 클래스가 결정합니다.

인터페이스를 사용하는 이유는 구현체를 변경하더라도 사용하는 코드를 수정하지 않기 위해서입니다. 구현체가 바뀌어도 사용하는 코드는 그대로 유지되기 때문에 결합도를 낮출 수 있습니다. 또한 새로운 기능을 추가할 때, 확장성이 좋습니다. 그리고 Mock 객체를 사용할 수 있어 테스트에도 용이합니다.

다만, 인터페이스와 구현체를 각각 만들어야 하기 때문에 프로젝트 규모가 작다면 복잡해질 수 있습니다. 또한 변경 가능성이 거의 없는 기능까지 인터페이스로 만들면 과도한 설계가 될 수 있습니다.

## [COMMON-173] MVC 패턴이 무엇이고, 각 구성 요소의 역할을 설명해 주세요.

## [COMMON-176] 결합도와 응집도가 무엇이고, 좋은 설계에서는 각각 어떻게 관리되어야 하는지 설명해 주세요.

답변:

좋은 설계는 결합도는 낮고 응집도는 높아야합니다. 왜냐하면 결합도가 낮으면 변경의 영향이 적고 응집도가 높으면 역할이 명확해지고 유지보수는 쉬워지기 때문입니다.

답변:

리팩토링은 소프트웨어의 외부 동작은 변경하지 않고 내부 코드 구조를 개선하는 작업입니다. 

목적은 가독성, 유지보수성, 확장성을 높이는 것이며 중복 코드를 제거하거나 메서드를 분리하거나와 같은 작업을 진행합니다. 

리팩토링 시에는 기능이 변경되지 않아야 하며 이를 검증하기 위해 테스트 코드가 중요합니다. 또한 한번에 너무 많은 변경을 하기보다는 작은 단위로 점진적으로 수정하고 변경 후마다 테스트를 수행하는 것이 좋습니다.

## [COMMON-179] 기술 선택 시 trade-off를 설명한다는 것은 어떤 의미인지 설명해 주세요.

답변:

기술 선택 시 Trade-off를 고려한다는 것은 특정 기술만이 항상 정답이라고 판단하는 것이 아니라 각 기술이 가진 장단점을 비교하고 현재 시스템의 요구사항에 맞는 선택을 하는 것을 의미합니다.

예를 들어 RDB는 데이터 정합성과 트랜잭션 처리에 강점이 있지만 대규모 수평 확장에는 제약이 있을 수 있고 NoSQL은 확장성이 좋지만 데이터 일관성 관리가 필요합니다. 따라서 트래픽 규모, 데이터 특성, 운영 복잡도, 비용 등을 종합적으로 고려하여 적절한 기술을 선택해야 합니다.

## [COMMON-180] 본인의 프로젝트에서 기술적 의사결정을 설명할 때 어떤 구조로 답변하면 좋을지 설명해 주세요.

답변:

프로젝트에서 기술적 의사결정을 설명할 때에는 먼저 기존 환경과 발생한 문제를설명하고 해결을 위해 고려했던 대안을 비교한 뒤 최종 선택 이유를 설명하는 방식이 좋습니다. 

단순히 특정 기술의 장점을 나열하는 것이 아니라 각 선택지의 장단점과 트레이드 오프를 설명하고 현재 요구사항에 왜 해당 기술이 적합했는지를 이야기해야 합니다. 마지막으로 도입 후 개선된 결과나 정량적인 효과까지 설명하면 설득력 있는 답변이 될 것입니다.
