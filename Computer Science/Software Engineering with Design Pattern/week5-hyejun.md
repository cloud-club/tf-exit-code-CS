## [COMMON-161] 객체지향 프로그래밍이 무엇이고, 주요 특징을 설명해 주세요.

답변: 객체지향 프로그래밍은 프로그램을 상태와 행동을 가진 객체들의 상호작용으로 구성하는 방식. 주요 특징으로 캡슐화, 상속, 다형성, 추상화가 있으며 이를 통해 변경에 유연하고 재사용하기 쉬운 코드를 만들 수 있다.

## [COMMON-162] 캡슐화, 상속, 다형성, 추상화에 대해 설명해 주세요.

답변: 캡슐화- 데이터와 관련 동작을 하나로 묶고, 내부 구현을 외부에서 직접 변경하지 못하도록 제한. 상속- 기존 클래스의 속성, 기능을 새로운 클래스가 물려받아 재사용하는 것. 다형성- 같은 인터페이스나 메서드 호출이 객체에 따라 다르게 동작. 추상화- 복잡한 내부 구현은 숨기고 필요 핵심 기능만 외부에 제공

## [COMMON-163] SOLID 원칙에 대해 설명해 주세요.

답변: SOLID는 변경과 확장에 유연한 객체지향 설계를 위한 다섯 가지 원칙,

SRP: 하나의 클래스는 하나의 변경 이유만 가져야 한다.
OCP: 확장에는 열려 있고 수정에는 닫혀 있어야 한다.
LSP: 하위 타입은 상위 타입을 문제없이 대체할 수 있어야 한다.
ISP: 사용하지 않는 기능에 의존하지 않도록 인터페이스를 분리해야 한다.
DIP: 구체적인 구현이 아니라 추상화에 의존해야 한다.

## [COMMON-164] 단일 책임 원칙이 무엇이고, 왜 중요한지 설명해 주세요.

답변: 단일 책임 원칙은 하나의 클래스나 모듈이 하나의 책임, 즉 하나의 변경 이유만 가져야 한다는 원칙. 책임을 분리하면 특정 기능을 수행했을 떄 다른 기능에 미치는 영향이 줄어들어 유지보수와 테스트가 쉬워짐

## [COMMON-165] 의존성 역전 원칙이 무엇이고, 어떤 장점이 있는지 설명해 주세요.

답변: 상위 모듈과 하위 모듈 모두 구체적인 구현이 아닌 인터페이스와 같은 추상화에 의존해야 한다는 원칙. 이를 적용하면 구현체를 쉽게 교체할 수 있고 테스트용 객체를 주입하기 쉬워져 확장성, 테스트 가능성이 높아짐.

## [COMMON-166] 인터페이스를 사용하는 이유와 장단점을 설명해 주세요.

답변: 인터페이스는 객체가 제공해야 할 기능의 규약을 정의하고, 사용하는 코드와 실제 구현을 분리하기 위해 사용. 구현체 교체, 확장이 쉽고 테스트 대역을 활용하기 좋다는 장점이 있음. 반면 불필요하게 사용하면 파일과 계층이 늘어나 코드가 복잡해질 수 있음.

## [COMMON-167] 추상 클래스와 인터페이스의 차이에 대해 설명해 주세요.

답변: 추상 클래스는 공통상태와 구현을 공유하려는 클래스 간 사용, 인터페이스는 서로 다른 클래스에 공통된 동작 규약을 부여할 때 사용. 일반적으로 클래스는 하나의 클래스만 상속가능하지만 여러 인터페이스 구현 가능. 따라서 공통구현이 중요하면 추상클래스, 역할과 규약이 중요하면 인터페이스가 적합.

## [COMMON-169] Singleton Pattern이 무엇이고, 장단점은 무엇인지 설명해 주세요.

답변: 클래스의 인스턴스를 하나만 생성하고 애플리케이션 전체에서 공유하도록 하는 패턴. 설정 관리자나 로깅 객체처럼 하나의 인스턴스가 필요한 경우 사용 가능. 자원관리가 쉽다는 장점이 있지만 전역상태를 만들어 결합도를 높이고 테스트와 동시성 관리를 어렵게 할 수 있음.

## [COMMON-170] Factory Method Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변: 객체 생성 코드를 별도의 메서드로 분리하고, 어떤 객체를 생성할지는 하위 클래스나 구현체가 결정하도록 하는 패턴. 사용하는 측이 구체 클래스의 생성 방식에 의존하지 않게 해줌. 결제수단, 알림채널처럼 조건에 따라 생성할 객체가 달라지는 경우 활용 가능

## [COMMON-171] Strategy Pattern이 무엇이고, 어떤 문제를 해결할 수 있는지 설명해 주세요.

답변: Strategy Pattern 은 여러 알고리즘을 각각 독립된 객체로 분리하고 실행 시점에 필요한 전략을 선택하는 패턴. 많은 조건문으로 처리하던 로직을 분리해 새로운 전략을 기존 코드 수정 없이 추가 가능. 할인 계산, 인증방식, 정렬 알고리즘 등에 사용 가능.

## [COMMON-172] Observer Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변: 한 객체의 상태가 변하면 이를 구독하느 여러 객체에 자동으로 알리는 패턴. 발행자와 구독자를 느슨하게 연결 가능, 이벤트 처리, 알림 시스템, UI 상태 변경 등에 사용. 구독 해제를 관리하지 않으면 메모리 누수나 불필요 호출 발생 가능

## [COMMON-173] MVC 패턴이 무엇이고, 각 구성 요소의 역할을 설명해 주세요.

답변: MVC는 애플리케이션을 Model, View, Controller로 분리하는 패턴
- Model: 데이터와 비즈니스 로직을 담당
- View: 사용자에게 화면을 표시
- Controller: 사용자 요청을 받아 Model을 호출하고 적절한 View로 연결
역할을 분리하여 ui와 비즈니스 로직을 독립적으로 변경하기 쉽게 만듦

## [COMMON-174] Layered Architecture가 무엇이고, 어떤 장단점이 있는지 설명해 주세요.

답변: 시스템을 표현, 비즈니스, 데이터 접근 등의 계층으로 나누고, 각 계층이 정해진 역할을 수행하도록 하는 구조. 책임이 명확하여 이해와 테스트가 쉽다는 장점이 있음. 반면 단순한 요청도 여러 계층을 거쳐야 하므로 코드 증가, 계층 간 의존성이 커지면 변경이 어려워짐

## [COMMON-175] 관심사의 분리가 무엇이고, 좋은 코드 구조에 왜 중요한지 설명해 주세요.

답변: 서로 다른 역할, 책임을 별도 모듈, 계층으로 나누는 설계 원칙. 예를 들어 비즈니스 로직, 데이터베이스 접근 코드를 분리하는 것. 이를 통해 한 기능을 변경했을 때 다른 영역에 미치는 영향을 줄이고 코드의 재사용성, 테스트 가능성, 유지보수성 높이기 가능

참고 자료:

---

## [COMMON-176] 결합도와 응집도가 무엇이고, 좋은 설계에서는 각각 어떻게 관리되어야 하는지 설명해 주세요.

답변: 결합도는 모듈들이 서로 의존하는 정도. 응집도는 하나의 모듈 내부 요소들이 같은 책임을 수행하는 정도. 좋은 설계는 모듈 간 결합도를 낮추고 모듈 내부 응집도를 높여야 함. 그러면 특정 모듈의 변경이 다른 모듈에 미치는 영향이 줄어듦

참고 자료:

## [COMMON-177] 테스트 코드가 필요한 이유와 단위 테스트, 통합 테스트의 차이를 설명해 주세요.

답변: 테스트 코드는 기능이 요구사항대로 동작하는지 검증하고, 변경으로 인해 기존 기능이 깨지는 회귀 오류를 빠르게 발견하기 위해 필요. 단위 테스트는 함수나 클래스처럼 작은 단위를 외부 의존성과 분리해 검증. 통합테스트는 데이터베이스, 외부 api, 여러 모듈이 실제로 함께 동작하는지를 검증

## [COMMON-179] 기술 선택 시 trade-off를 설명한다는 것은 어떤 의미인지 설명해 주세요.

## [COMMON-180] 본인의 프로젝트에서 기술적 의사결정을 설명할 때 어떤 구조로 답변하면 좋을지 설명해 주세요.

답변: 다음 구조로 설명하면 좋습니다.

문제: 어떤 문제를 해결해야 했는지 설명합니다.
요구사항과 제약: 성능, 비용, 일정, 인력 등 고려 조건을 제시합니다.
대안 비교: 검토한 기술과 각각의 장단점을 설명합니다.
선택 근거: 프로젝트 상황에서 해당 기술을 선택한 이유를 설명합니다.
적용 결과: 성능 개선이나 작업 시간 단축 등 결과를 수치로 제시합니다.
한계와 개선점: 선택으로 발생한 단점과 향후 개선 방향을 설명합니다.

예를 들어 “Terraform이 유명해서 선택했다”가 아니라 “반복되는 AWS 리소스 구성을 표준화하고 변경 이력을 관리해야 했기 때문에, 초기 학습 비용을 감수하고 Terraform을 선택했다”와 같이 답변하는 것이 좋습니다. --라고하네요~
