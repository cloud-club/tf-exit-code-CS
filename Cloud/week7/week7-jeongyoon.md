## [ROLE-042] Multi-AZ 구성에서 Load Balancer, Subnet, Instance 또는 Pod를 어떻게 배치해야 하는지 설명해 주세요.

## [ROLE-043] Auto Scaling 정책을 CPU, Memory, Request Count, Custom Metric 기준으로 설계할 때 각각의 장단점을 설명해 주세요.

## [ROLE-044] 클라우드 환경에서 Scale Out과 Scale Up을 선택하는 기준을 설명해 주세요.

답변:

- Scale Out
    - 인스턴스나 파드의 개수를 늘리는 방식
    - 웹 애플리케이션처럼 요청을 여러 인스턴스에 분산할 수 있는 서비스에 적합
- Scale Up
    - 하나의 서버나 인스턴스의 CPU, Memory 등 리소스를 증가시키는 방식
    - 여러 인스턴스로 분산하기 어려운 데이터베이스나 상태 기반 시스템 적합

⇒ 일반적으로 애플리케이션은 Scale Out이 가능하도록 Stateless하게 설계, 단일 인스턴스의 성능 자체가 부족한 경우는 Scale Up을 함께 고려

## [ROLE-045] Kubernetes에서 Node, Pod, ReplicaSet, Deployment의 관계를 설명해 주세요.

답변:

```cpp
Cluster
  │
  ├── Node
  │    │
  │    └── Pod
  │          │
  │          └── Container
  │
  └── Deployment
         │
         ▼
      ReplicaSet
         │
         ▼
        Pod
```

- Node
    - Pod가 실제로 실행되는 서버입니다.
- Pod
    - 컨테이너를 실행하는 가장 작은 배포 단위입니다.
- ReplicaSet
    - 설정된 Replica 수만큼 Pod가 항상 유지되도록 관리하며 Pod가 장애로 삭제되면 새로운 파드를 생성합니다.
- Deployment
    - ReplicaSet을 상위에서 관리하면서 애플리케이션의 롤링 업데이트 같은 배포 전략을 담당합니다

⇒ Deployment가 ReplicaSet을 관리하고 ReplicaSet이 Pod의 개수를 유지하며 생성된 Pod는 쿠버네티스 스케쥴러에 의해 적절한 Node에 배치되는 구조입니다.

## [ROLE-046] Kubernetes Service의 ClusterIP, NodePort, LoadBalancer 타입 차이를 설명해 주세요.

답변:

- 쿠버네티스 서비스는 여러 파드에 대한 안정적인 네트워크 접근 지점을 제공하는 서비스입니다.
- ClusterIP는 가장 기본적인 타입으로 클러스터 내부에서만 접근할 수 있어 서비스 간 내부 통신에 주로 사용됩니다.
- NodePort는 모든 노드의 특정 포트를 통해 외부에서 서비스에 접근할 수 있도록 합니다.
- 로드 밸런서는 클라우드 환경에서 외부 로드밸런스를 생성하거나 연동하여 외부 트래픽을 쿠버네티스 서비스와 파드로 전달하는 방식입니다.
- 따라서 일반적으로 내부 통신에는 clusterIP를 사용하고 간단한 외부 노출에는 NodePort를 사용할 수 있으며 클라우드 환경에서 외부 서비스를 안정적으로 제공하는 경우에는 로드밸런서를 사용합니다.

## [ROLE-048] Kubernetes에서 ConfigMap과 Secret의 차이를 설명하고, Secret 사용 시 주의할 점을 설명해 주세요.

답변:

- ConfigMap
    - 애플리케이션의 일반적인 설정값을 저장하는 데 사용
    - 서버주소, 환경 설정, 로그 레벨 등을 값이 들어갈 수 있음
    
    ⇒ 코드나 컨테이너 이미지에 설정값을 직접 넣지 않고 외부에서 관리하기 위해 사용
    
- Secret
    - 비밀번호, 인증 정보처럼 민감 데이터를 저장하기 위한 리소스
    - 쿠버네티스 시크릿은 단순 Base64 인코딩일 수 있기 때문에 암호화된 비밀번호라고 생각하면 안됩니다. 그래서 git 저장소에도 커밋을 하면 안되고 로그에서도 해당 시크릿이 노출되지 않도록 해야함
    - 필요에 따라 외부 시크릿 매니저나 Vault와 같은 별도의 시크릿 관리 시스템을 연동하는 것도 고려할 수 있습니다.

## [ROLE-050] Kubernetes에서 OOMKilled가 발생하는 원인과 대응 방법을 설명해 주세요.

답변:

- 쿠버네티스에서 OOMkilled는 컨테이너가 사용할 수 있는 메모리가 부족해 커널에 의해 종료된 상태입니다.
- 핵심적인 원인은 주로 컨테이너의 실제 메모리 사용량이 설정된 메모리 리밋을 초과했기 때문입니다.

## [ROLE-051] Kubernetes에서 Readiness Probe, Liveness Probe, Startup Probe의 차이를 설명해 주세요.

답변:

- Readiness Probe
    - 이 파드가 지금 트래픽을 받을 준비가 되었는가를 확인합니다. 해당 probe가 실패하면 해당 파드를 서비스의 트래픽 대상에서 제외합니다.
- Liveness Probe
    - Container가 실행 중이긴 한데 실제로 정상적으로 동작하고 있는가를 확인합니다. 프로세스는 살아있지만 데드락이나 무한 루프 때문에 실제 요청을 처리하지 못하는 경우가 있습니다. 이 경우에 프로브가 계속 실패하면 컨테이너를 재시작합니다.
- Startup Probe
    - 애플리케이션이 정상적으로 시작되었는지 확인하는 프로브입니다.
    - 애플리케이션 시작 시간이 오래 걸리는 경우에 Liveness Probe가 너무 빨리 실행되면 아직 시작 중인 애플리케이션을 장애로 판단할 수 있습니다. 이를 방지하기 위해 사용합니다.

## [ROLE-052] Rolling Update 과정에서 무중단 배포를 위해 고려해야 할 Kubernetes 설정을 설명해 주세요.

답변:

- 중요한 설정은 새 파드가 트래픽을 받을 준비가 된 것을 확인한 후 기존 파드를 제거하고 배포 중에도 최소한의 파드 수를 유지해야 합니다.
- 롤링 업데이트는 기본적으로 한번에 전부 죽이는 것이 아니라 점진적으로 교체하기 때문에 이 과정에서 기존 파드를 너무 빨리 제거하거나 새 파드가 준비되기 전에 트래픽을 받으면 서비스가 끊길 수 있습니다.
- maxUnavailable
    - 업데이트 중 사용할 수 없는 파드를 최대 몇 개까지 허용할 것인지 설정하는 값
- maxSurge
    - 업데이트 중 원래 Replica 수보다 추가로 생성할 수 있는 파드의 최대 개수
- 또한 Readiness Probe를 통해 새로운 파드가 실제로 트래픽을 처리할 준비가 된 경우에만 서비스의 엔드포인트에 포함되도록 해야 합니다.

## [ROLE-053] CI/CD 파이프라인에서 Build, Test, Image Build, Push, Deploy 단계의 흐름을 설명해 주세요.

답변:

- 예를 들어 개발자가 코드를 수정하고 깃에 푸시를 했다고 하면
- Build
    - 단계에서는 작성한 소스 코드를 실제 실행 가능한 결과물로 만드는 작업
- Test
    - Build가 성공했다고 코드가 정상이라는 의미는 아니기 때문에 테스트를 수행
- Image Build
    - Build 결과물인 JAR 파일을 Container Image로 만드는 단계
    - 애플리케이션과 실행 환경을 묶어서 컨테이너 이미지로 만드는 과정
- Push
    - 만들어진 컨테이너 이미지를 레지스트리에 저장하고 배포 가능한 상태로 만드는 과정
- Deploy
    - 새로운 이미지를 실제 쿠버네티스 환경에 반영, 배포 진행

## [ROLE-056] Infrastructure as Code에서 상태 파일 State가 중요한 이유와 관리 시 주의할 점을 설명해 주세요.

답변:

- Infrastructure as Code에서 State는 코드로 정의한 리소스와 실제 인프라 리소스의 매핑 정보와 현재 상태를 관리하는 파일입니다.
- Terraform은 State를 기준으로 현재 인프라 상태와 코드에서 정의한 원하는 상태를 비교하여 어떤 리소스를 생성, 수정, 삭제해야 하는지 판단합니다.
- State에는 민감한 정보도 포함될 수 있기 때문에 Git에 직접 저장하지 않고 팀 환경에서는 Remote Backend를 사용해 중앙에서 관리하는 것이 좋습니다.
- 여러 사용자가 동시에 변경하며 충돌하지 않도록 State Lock을 적용하고 암호화와 접근 권한 제어, 백업 및 버전 관리도 생각해야 합니다.

## [ROLE-057] 클라우드 비용이 갑자기 증가했을 때 어떤 순서로 원인을 분석할 수 있는지 설명해 주세요.

답변:

- 먼저 비용이 증가하기 시작한 시점을 확인하고 해당 시점의 배포나 인프라 변경 이력을 비교합니다.
- 이후 전체 비용에서 Compute, Storage, Network 등 서비스별로 비용을 분류하여 가장 크게 증가한 항목을 찾습니다.
- 그리고 해당 서비스 내부에서 어떤 리소스 사용량이나 개수가 증가했는지 분석합니다
- 쿠버네티스 환경이라면 노드, 파드의 개수, HPA나 KEDA, 클러스터 오토스케일러 동작 여부와 리소스 리퀘스트 등을 확인합니다.
- 정상적으로 사용량이 늘었기 때문에 비용이 늘어난건지, 설정 오류나 장애로 인해 늘게 된건지 구분이 필요합니다.

## [ROLE-058] 모니터링 지표 중 CPU 사용률, Memory 사용률, Error Rate, Latency, Throughput이 각각 무엇을 의미하는지 설명해 주세요.

답변:

- CPU 사용률
    - 단순하게 CPU가 얼마나 사용되고 있는지, 얼마나 바쁜지를 의미합니다.
    - 사용률이 지속적으로 높으면 처리 성능 저하, 응답 시간 증가 발생
- Memory 사용률
    - 실행 공간이 얼마나 남았는가
    - OOMkilled, 메모리 누수 의심
- Error Rate
    - 전체 요청 중 실패한 비율로 서비스의 정상 여부를 확인하는 핵심 지표입니다.
- Latency
    - 사용자가 요청을 보낸 시점부터 응답을 받을 때까지 걸리는 시간입니다.
- Throughput
    - 일정 시간 동안 시스템이 처리한 요청의 양
    - 시스템의 처리량과 트래픽 변화를 확인

## [ROLE-059] 장애 대응에서 Alert의 임계값을 설정할 때 고려해야 할 점을 설명해 주세요.

답변:

- alert는 자주 발생하게 되면 순간적인 스파이크에도 alert가 발생할 수 있고 간격이 너무 높으면 실제 장애를 너무 늦게 감지할 수 있습니다.
- 따라서 임계값과 함께 일정 시간 이상 지속되는 조건을 설정하여 일시적인 변동과 실제 장애를 구분하는 것이 중요합니다.
- 또한 CPU가 메모리의 값만을 보기 보다는 Error Rate나 Latency처럼 사용자에게 직접 영향을 주는 지표를 함께 고려해야 합니다.
- 그리고 Warning, Critical과 같은 타입을 구분해 대응 우선순위를 설정할 수 있습니다.

## [ROLE-060] 장애 발생 후 Postmortem을 작성하는 이유와 포함해야 할 내용을 설명해 주세요.

답변:

- Postmortem
    - 서비스의 장애가 발생하고 해결됐다고 끝내는 것이 아니라 이후에
    - 정확히 무슨 일이 발생했는지, 왜 장애가 발생했는지, 대응 과정에 문제는 없었는지, 재발을 어떻게 방지할 것인지를 정리하는 것
- 이를 작성하는 이유는 우선, 장애의 근본 원인을 찾기 위해서입니다. 그리고 장애 대응 과정을 개선하기 위해 작성합니다.
- 그렇기 때문에 장애 요약, 어떤 서비스에 얼마나 영향이 있었는지, 타임라인, 어떻게 발견하게 되었는지 등을 함께 작성합니다.
